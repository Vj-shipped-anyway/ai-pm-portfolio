# Data for project 73

Synthetic. Generated by `_generate.py` with a fixed seed (73), so a rerun reproduces every file byte for byte. Nothing here is a real message, institution or format. The legacy format is invented. The ISO element names follow the pacs.008 naming in a flat path view; the lengths and mandatory flags are my simplification and have not been checked against any message specification (assumption, 🟡).

## The mapping under review (the tool's input directory is this folder)

| File | What it holds |
|---|---|
| `legacy_fields.csv` | 20 legacy fields: `field`, `max_len`, `kind` (text, digits, amount, date, code), `codes` (allowed values, `\|` separated) |
| `iso_elements.csv` | 20 ISO elements: `path`, `max_len`, `kind` (text, decimal, date, code), `mandatory` (Y or N), `codes` |
| `mapping.csv` | 19 rows: `row_id`, `legacy_fields`, `iso_path`, `transform` (copy, join_lines, amount_implied2, date_yyyymmdd, code_table, const, drop), `param` (a separator, a table name or a constant) |
| `code_tables.json` | the code tables: legacy code to ISO code |

The intended mapping has 21 rows. The reviewed mapping has two removed (the sender reference to the group message identifier, and the third originator address line) and one entry removed from the charge-code table (legacy code `O`). Two fields have limits that do not fit: the beneficiary account holds 35 characters and its element takes 34; the four remittance lines hold 143 characters with separators and the element takes 140. That makes 5 planted mapping defects, listed in `mapping_truth.csv`. The same file lists 3 harmless rows that a careless rule would flag: a field dropped on purpose (`INTNOTE`) and two mandatory elements filled by a constant.

## The messages and the builds

| File | What it holds |
|---|---|
| `legacy_messages.json` | 23 legacy messages, fixed-width (values padded to the field size): 20 typical (`M01` to `M20`) and 3 boundary probes (`P1` to `P3`) with every field filled to its limit and the codes cycled together |
| `iso_outputs.json` | the ISO elements each of 10 converter builds produced for each message, 230 pairs in all |
| `builds.csv` | the 10 builds: `build`, `defect`, `legacy_field`, `iso_path`, `param`, `benign`, `description` |
| `truth_events.csv` | every place a build's output differs from the lossless value, recorded by the build as it ran: `build`, `msg`, `subject`, `kind`, `category`. The label comes from the converter, not from the checker |
| `example_pairs.json` | three pairs behind `python3 iso20022_map_check.py --demo` |

Builds: B01 clean; B02 clean but pads text and writes amounts without trailing zeros (162 harmless variations in all: 154 padding, 8 amount format); B03 cuts the originator name at 33 characters; B04 cuts the second originator address line at 33; B05 never writes the receiver identifier; B06 rounds amounts to whole units; B07 swaps month and day in the value date; B08 strips leading zeros from the beneficiary account; B09 swaps the first two originator address lines; B10 drops the beneficiary account when TYP is 16 and CHGS is S. No message has that combination, so B10 never fires.

Events by category: 212 planted converter and capacity defects (90 capacity cuts that every build makes when a value is longer than its element, and 122 build defects), 162 harmless variations, and 390 footprints of the mapping gaps (the third address line lost, a message identifier the mapping does not explain, a charge code that fell back to a default). Hard cases kept in on purpose: values exactly at a limit, whole-dollar amounts that survive rounding, a month equal to the day, padded text, amounts without trailing zeros.
