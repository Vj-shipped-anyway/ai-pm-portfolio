# Data for project 33

Synthetic. Generated by `_generate.py` with a fixed seed (`SEED = 33`, the folder number, not re-rolled), so a rerun reproduces every file byte for byte. Nothing here comes from a real bank, customer, reviewer or case.

| File | What it holds |
|---|---|
| `proposals.csv` | 1000 rows, the scorecard's first input: `case_id`, `segment`, `day`, `proposed_outcome`, `proposed_value`, `confidence`. A blank `proposed_outcome` means the agent abstained (56 of the matched cases). `day` is a whole number from 0; the scorecard uses `day // 7` as the week. `proposed_value` is a refund amount when the proposal is REFUND |
| `outcomes.csv` | 989 rows, the second input: `case_id`, `human_outcome`, `human_value`, `handled_by`. 986 match a proposal; 3 (`M-001` to `M-003`) are cases keyed by hand with no proposal. 14 proposals have no outcome yet |
| `case_truth.csv` | 1000 rows: `case_id`, `true_outcome`, `planted`. What should have happened. The scorecard never reads it; the step scripts use it to say whether a flag was right |
| `planted_problems.csv` | 8 rows: the 5 problems and 3 look-alikes below, with `real` set to 1 or 0 |

The scenario: a card-dispute agent proposes one of four outcomes (REFUND, DENY, REQUEST_DOCS, ESCALATE_FRAUD) in shadow mode. People record their own outcome, with a refund amount when they refund. Six segments (`card_present`, `online`, `recurring`, `business`, `joint_account`, `intl_atm`), 14 weeks of arrivals and nine reviewers (`W01` to `W09`).

## How the data is generated

The truth of each case is drawn first, from a mix per segment. The agent's proposal and the person's outcome are then drawn from the truth by two separate processes with their own error rates, and the scorecard sees only the two results. 🟡 The rates are design values that I set to make each planted problem large enough to see in a group of 60 to 75 cases. I ran the scorecard and changed some of them (case count, size of the drift, how strict one reviewer is, the value-error rate) before settling. The seed was not re-rolled.

Planted real problems (5; weeks 12 and 13 count as two):

- `joint_account` segment: agent error rate 0.18 against 0.01 to 0.02 elsewhere
- weeks 12 and 13: 0.20 added to the agent error rate, as after a model change
- `ESCALATE_FRAUD`: the agent abstains on 35% of these cases, 2% to 8% on the others
- reviewer `W07`: the person deviates from the truth on 20% of cases against 0.5% for the rest

Planted look-alikes that are not problems (3), each with a few forced disagreements that a flag with no minimum size would raise:

- the `intl_atm` segment, 8 cases, 3 agent misses
- week 6, a holiday week with a handful of cases, 4 agent misses
- reviewer `W09`, 6 cases, 3 deviations by the person

Planted hard case (16): cases where the agent and the person agree on the same wrong outcome (`planted` = `shared_wrong` in `case_truth.csv`). Two files cannot show them.

Other noise: the agent's refund amount is 1.50 too high on 2% of its REFUND proposals, so the outcome agrees and the value does not. The agent's stated confidence is higher when it is right, and wrong proposals can still carry a high one.

## What the data does not contain

- A real queue, a real agent or a real reviewer.
- A second reviewer on any case, or any measure of how often two people would disagree.
- A held-out period. Nothing is fitted, but the planted rates were tuned to be visible.

## Using your own data

Export two files with the columns above and keep the headers. `proposals.csv` needs one row per case the agent saw; `outcomes.csv` one row per recorded outcome. Blank `human_value` and `proposed_value` are fine. `case_truth.csv` and `planted_problems.csv` exist only because this data is synthetic.
