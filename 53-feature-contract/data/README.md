# Data for project 53

Synthetic. Generated by `_generate.py` with a fixed seed (`SEED = 53`), so a rerun reproduces every file byte for byte. Nothing here comes from a real feature table, bank or employer.

| File | What it holds |
|---|---|
| `contract_credit_triage.json`, `contract_card_fraud.json`, `contract_aml_alerts.json` | The three contracts, one per feed, 7 fields each. These are the rules the tool checks |
| `batches.jsonl` | 90 deliveries: `batch_id`, `feed`, `columns` (the header as delivered) and `rows` (100 rows of text, an empty string is a null) |
| `batch_truth.csv` | The planted change per batch: `change_kind`, `truth_class` (`bad` or `ok`), `changed_field` and `rows_changed`. The label comes from the change that was planted, not from the checker |
| `example_batch.csv` | The worked example behind `python3 feature_contract.py --demo`: 100 credit rows in which `dti_ratio` arrives as a percent |

The generator keeps two parts apart. The process draws the values (for example `annual_income_usd` from a log-normal, `fico_score` from a clipped normal) and applies the planted change; it never reads the contracts. The contracts are written as a data owner would write them, with round numbers wider than the values the process draws. The declared maximum of `txn_total_30d_usd` is 10,000,000.

Planted changes (90 batches): 47 bad and 43 ok.

- bad: column dropped 4, column renamed 4, numbers sent as text such as `$1,234.50` or `34.5%` 5, integer sent with a fraction 3, null surge to 25 to 40 rows 5, ratio sent as a percent 5, sentinel -999 in 5 to 8 rows 5, unseen category in 15 to 30 rows 4, dollars sent as cents 4, days sent as weeks or months as years 5, missing values zero-filled in 15 to 20 rows 3
- ok: unchanged 15, columns reordered 5, harmless extra column 5, exactly 4 nulls in a field that allows 5.0% 5, values exactly on a bound 4, integers written as `12.0` 4, one or two rows with a typo far outside the range 5

The last four ok kinds are hard on purpose: each is something a stricter check could mistake for a problem. Two bad kinds are hard in the other direction: zero-fill, and days sent as weeks or months as years, stay inside the declared type, range and null rate, and the checker cannot see them. A third, dollars sent as cents, passes when the field's declared range is wide enough to hold the new scale (2 of 4).

## Assumptions (🟡 modeled, mine, not taken from any rule)

- A delivery is 100 rows.
- `max_bad_rate` is 2.0%: up to two rows in a hundred may break a type, range or allowed-values rule. This decides that the one-or-two-row typos are harmless.
- `max_null_rate` is 5.0% on the four fields that may be null (`ltv_ratio`, `annual_income_usd`, `device_risk_score`, `high_risk_geo_share`) and 0 on the rest.
- An unseen category in an enum field counts as a bad change, and a harmless extra column counts as ok; both are labels I chose when planting.
- Integers written as `12.0` are accepted as integers.
