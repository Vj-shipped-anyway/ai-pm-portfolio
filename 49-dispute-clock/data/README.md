# Data for project 49

Synthetic. Generated by `_generate.py` with a fixed seed (49), so a rerun reproduces every file byte for byte. Nothing here comes from a real bank, customer, dispute or employer. The dates are invented and the calendar is a modeled one.

**🟡 Assumptions, all of them.** The five windows, the holiday list, the rule that a clock starts at first contact, the rule that a due date on a day off stays there, and the rule that the credit clock is also met by finishing the investigation are assumptions of a modeled bank. None is read from a rule. They are to be confirmed with counsel before anyone relies on them.

| File | What it holds |
|---|---|
| `policy.csv` | The 5 clocks: `clock_id`, `clock_name`, `applies_to` (all, standard, extended, credit_eligible), `window_days`, `day_type` (business or calendar), `anchor_event` (the dispute column the clock starts from), `satisfied_by` (one or more dispute columns, the earliest counts), `basis`, `note` |
| `holidays.csv` | 11 weekdays on which the modeled bank is closed in 2026 |
| `as_of.txt` | The date every step reads the clocks at: 2026-09-30 |
| `disputes.csv` | 150 disputes, as a case system would hold them |
| `truth.csv` | One row per clock that applies (524): the status the generator planted, the planted due date, and the hard-case tags |
| `example_disputes.csv` | The worked example behind `python3 dispute_clock.py --demo` (one unauthorized-card dispute first reported on 2026-09-04) |

## `disputes.csv`

| Column | What it is |
|---|---|
| `dispute_id` | `DSP-0001` onward, in order of first contact |
| `dispute_type` | unauthorized_card 49, billing_error 33, merchant_dispute 29, unauthorized_transfer 25, duplicate_charge 14 |
| `window_class` | As recorded in the case system: standard 133, extended 17. The tool reads this field and nothing else to pick the investigation window |
| `credit_eligible` | 1 for the two unauthorized types (74 disputes), else 0 |
| `first_contact_on` | The day the customer first told the bank, by any channel, between 2026-05-06 and 2026-09-28. This is where the clocks start |
| `logged_on` | The day the case was opened in the queue. Later than first contact on 98 disputes, because of a weekend or a lag of up to 5 business days |
| `acknowledged_on`, `provisional_credit_on`, `concluded_on`, `final_notice_on` | When each step happened. Empty means it had not happened at the as-of date: 22 disputes were never acknowledged, 107 were concluded |
| `info_requested_on`, `info_received_on` | When the bank asked the customer for information and when it arrived. Set on 22 disputes. The tool does not read them |

## `truth.csv`

| Column | What it is |
|---|---|
| `dispute_id`, `clock_id` | Join keys |
| `planted_status` | on_time 297, late 93, breached 58, running 33, not_started 43 |
| `planted_due` | The due date the generator reached by stepping forward, with the pause added for a paused investigation. Empty for a clock that has not started |
| `hard_case` | Tags joined by `\|`: `logged_late` 241 clocks, `boundary` 109 (the step happened exactly on the due day), `holiday` 57 (a business-day window that crosses a weekday holiday), `pause` 22, `misrecorded` 6 |

Clocks by id: DC1 150, DC2 74, DC3 133, DC4 17, DC5 150.

**How the truth is made.** The generator picks, for each step, a plan (on time, on the due day, late by 1 to 9 business days, or never) and places the date. It then labels each clock by counting elapsed days between the start and the event, and checks that against its own stepped due date before it writes the row. The tool does the stepping and the comparison in `src/`; it never reads this file. The generator and the tool share an author, and the truth is the generator's plan, so agreement shows the tool does what the plan says, not that the plan is right.

**Three planted hard cases.**

- *Paused investigations.* On 22 disputes the bank waited for the customer, and the plan counts the investigation as paused for that long. The tool ignores the pause. It calls some of those clocks late or breached when the plan says they were on time.
- *Wrongly recorded window class.* On 6 of the 17 disputes recorded as extended, the 60-day window never applied. The truth uses 30 days; the tool trusts the recorded class and gives them 60.
- *Hard negatives.* Steps that land exactly on the due day, and business-day windows that cross a holiday, are the cases a calendar-day count gets wrong. The tool should get them right.
