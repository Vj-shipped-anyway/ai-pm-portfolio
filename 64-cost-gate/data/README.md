# Data for project 64

Synthetic. Generated by `_generate.py` with a fixed seed, so a rerun reproduces every file byte for byte. Nothing here comes from a real eval, bank, vendor or employer.

| File | What it holds |
|---|---|
| `budget.json` | The budget the gate reads: prices for 3 models, `min_items` 30, an overall ceiling and a ceiling for each of 5 slices, all in USD per correct answer |
| `eval_runs.csv` | 41 eval runs of 236 items each: the baseline run (`cr_id` BASE) and 40 change requests (CR-001 to CR-040). Columns: `cr_id`, `item_id`, `slice`, `model`, `correct`, `input_tokens`, `output_tokens` |
| `cr_truth.csv` | The planted change per change request, `truth_class` (over_budget or within_budget), `true_worst_ratio` (the highest of true cost per correct answer divided by its ceiling, over the whole run and every slice) and `true_scopes_over` |
| `example_results.csv` | One run in the format the command line reads (no `cr_id`): the first slice-regression change request. It is what `python3 cost_gate.py --demo` checks |

## How a run is made

Each slice has an item count, an accuracy, and a mean number of input and output tokens on model-a. For every item the generator draws correct or not with the slice's accuracy, and a token count equal to the slice mean times a factor: uniform from 0.5 to 1.5, except one item in twenty (a long conversation) where it is uniform from 2.0 to 3.0. The mean factor is 1.075.

| Slice | Items | Accuracy | Mean input tokens | Mean output tokens |
|---|---|---|---|---|
| balance_inquiry | 64 | 0.92 | 420 | 90 |
| dispute_status | 56 | 0.78 | 900 | 220 |
| fee_questions | 56 | 0.84 | 700 | 180 |
| card_services | 48 | 0.86 | 600 | 140 |
| wire_exceptions | 12 | 0.62 | 1300 | 380 |

Prices are synthetic parameters in USD per 1,000 tokens (input, output): model-a 0.0030 and 0.0150, model-b 0.0024 and 0.0120, model-c 0.0051 and 0.0255. model-a and model-b are the two price points of project 13; model-c is invented for the swap cases.

## Where the truth comes from

The truth is not computed by the gate. For each change request the generator takes the parameters it used (accuracy, mean tokens, model), computes the expected cost per correct answer of every slice and of the whole run in closed form, and compares each with its ceiling. A change request is over budget if any of them is over.

🟡 Assumptions, named: the overall ceiling is the baseline's expected cost per correct answer times 1.15; each slice ceiling is that slice's baseline times 1.25; `min_items` is 30. None comes from a standard.

## Planted changes (40)

unchanged 8, near budget but fine (tokens scaled by 1.09 to 1.12 everywhere) 6, richer prompt with better answers (input tokens up 30% to 40%, accuracy up 0.06 to 0.10) 5, model swap to a dearer model 3, verbose output (output tokens up 70% to 100%) 3, accuracy drop with the same tokens 3, cheaper model that answers much worse 3, slice regression (one of balance_inquiry or card_services costs 1.6 to 1.7 times as much) 4, small overshoot of the whole-run ceiling (tokens scaled by 1.16 to 1.20) 3, regression inside the 12-item slice (wire_exceptions costs 1.9 to 2.1 times as much) 2.

Truth: 21 over budget and 19 within. Four kinds are hard on purpose: the near-budget and richer-prompt runs are within budget and could raise a false alarm (a cost-per-call check fails 3 of the 5 richer-prompt runs), and the small overshoot and the thin-slice regression are over budget and sit where the gate cannot see them.
