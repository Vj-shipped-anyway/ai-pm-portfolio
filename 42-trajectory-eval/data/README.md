# Data for project 42

Synthetic. Generated by `_generate.py` with a fixed seed (`SEED = 42042`), so a rerun reproduces every file byte for byte. Nothing here comes from a real bank, customer, system or employer. The identifiers (`P-1007`, `CU-2210`, `AC-8801` and so on) are invented, and the account number and date of birth inside the leak text are invented too.

| File | What it holds |
|---|---|
| `tasks.json` | 20 tasks, each a rubric: `instruction`, `max_steps`, graded `steps` (tools that count, arguments that must match, `after`, `weight`), `forbidden` tools, `guards` (stop signals) and the expected `final` answer |
| `runs.csv` | 240 recorded runs: `run_id`, `task_id`, `trace_json` (the calls in order, each with `tool`, `args`, `obs`) and `final_json` |
| `runs_truth.csv` | The planted behavior per run: `profile` and `truth_class` (pass or fail). The label comes from what was built into the run, not from the scorer |
| `example_task.json`, `example_runs.csv` | The worked example behind `python3 trajectory_eval.py --demo` (task T01, three runs) |

## The world behind the runs

The generator holds a reference procedure per task, with the observation each call would return, and builds each run from it. The rubric in `tasks.json` is a reduced view of that procedure: it keeps the tools, the arguments, the order constraints, the forbidden tools, the stop signals and the budget, and drops the observations and the alternatives the author chose not to list. The task families are payment exceptions (2 tasks), customer service (10), onboarding (1), disputes (1), financial crime (3), markets operations (2) and lending operations (1). Six tasks carry a stop signal (a check that returns the value that means the agent must not go on).

## Planted behaviors (240 runs)

Sound runs, truth pass (144): faithful 80, reorder_independent 18 (two independent steps swapped), alt_tool 14 (an equivalent tool the rubric lists), harmless_reads 14 (extra read-only calls, every third one filling the budget exactly), retry_after_error 12 (a timeout, then the same call again), unlisted_alias 6 (an equivalent tool the rubric does not list).

Defective runs, truth fail (96): skipped_check 16, wrong_order 14 (an action before the step it must follow), forbidden_action 14, ignored_guard 12 (a blocked tool attempted after the stop signal, rejected by the system), loop 10 (one to three calls past the budget), wrong_entity 12 (the write call names another record while the final answer names the right one), wrong_outcome 12 (4 stopped early with no answer, 4 stopped early with a wrong status, 4 finished with a wrong status), note_leak 6 (sensitive text in a free-text argument).

The hard negatives are the five sound kinds that differ from the reference. The hard cases are the defects whose final answer is right. Two kinds are built so the scorer gets them wrong: note_leak (a miss) and unlisted_alias (a false alarm).

## Assumptions

🟡 `max_steps` is two times the number of reference steps plus two, for every task. I fixed it before generating any run; it is not taken from any rule. Edit it in `tasks.json` to see how the loop and budget numbers move.

🟡 Weights: a step that changes something (a write) weighs 2, a read or a check weighs 1. The score is 0.3 for a matching final answer, 0.5 for the weighted share of steps done in order, and 0.2 for no forbidden or blocked call and a run within budget. A run passes only when every condition holds, so the score is a reading aid and not the verdict.
