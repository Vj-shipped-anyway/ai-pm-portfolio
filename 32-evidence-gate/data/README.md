# Data for project 32

Synthetic. Generated by `_generate.py` with a fixed seed (`SEED = 32`), so a rerun reproduces every file byte for byte. Nothing here comes from a real repository, bank, use case or employer. Use case ids, owner units and file paths are invented, and the external links use the reserved `.invalid` domain.

| File | What it holds |
|---|---|
| `tier_evidence.csv` | The tier-to-evidence table: 11 evidence items, the tier each is first required at, and a freshness limit in days |
| `registry.csv` | 33 registered use cases and their registry tier (the register the gate reads) |
| `use_cases.csv` | All 40 use cases with the true tier, the registry tier and `registry_status` (`current`, `stale_understated`, `unregistered`). Used only to score |
| `pr_cases.csv` | 107 pull request descriptions: `pr_id`, `body`. The only column the gate reads |
| `pr_truth.csv` | The planted state per pull request: `use_case_id`, `true_tier`, `defect_kind`, `truth_class` (`should_block`, `needs_review`, `fine`) and `bad_items`. Used only to score |
| `repo_files.txt` | The file listing of the made-up repository (205 paths), one per line, as `git ls-files` would print it |
| `example_pr_body.md`, `as_of.txt` | The worked example behind `python3 evidence_gate.py --demo` (a tier-3 use case declared at tier 2, with one stale item) and the fixed as-of date, 2026-10-16 |

## The tier-to-evidence table

The 11 items, their ids and their first tiers follow the checklist in [project 11](../../11-tiergate-ai-usecase-intake/data/README.md): tier 1 owes E01 and E02, tier 2 adds E03 and E04, tier 3 adds E05 to E08, tier 4 adds E09 to E11. A higher tier owes everything below it. The idea of a freshness limit per item comes from the gate criteria in [project 24](../../24-portfolioboard-ai-program-portfolio/data/README.md).

🟡 **The `max_age_days` values are assumptions of this project**, chosen so that the fast-moving items (the evaluation results, the sign-off) expire sooner than the slow ones (the privacy review). They are not taken from any rule. 🟡 The limit is inclusive: evidence dated exactly `max_age_days` before the as-of date is still valid; one day older is stale. That is a convention I picked.

## How the truth is decided

The generator builds each pull request from a structured spec: a use case with a true tier, a declared tier, and one record per evidence item with its planted state (ticked or not, file real or not, content right or not, date in range or not). The truth label is computed from that state at the use case's **true** tier. The gate never sees the spec; it parses the rendered text, the registry and the file listing. A pull request is `should_block` when a required item is not truly valid, `needs_review` when the evidence is complete but the declared tier differs from the true one, and `fine` otherwise.

**The same author wrote the planted cases and the rules.** Every finding kind in the gate exists because I planted a case for it, so the results are a ceiling for these rules, not a rate on real descriptions.

Half of the descriptions keep the template's comment block, which holds an example evidence line. The gate must not count it.

## What this data cannot tell you

How often real authors skip the template, how long real evidence takes to go stale, or how real registries drift. Those are generator choices. The set is dense in problems on purpose: 59 of 107 should be blocked, so that every rule is exercised several times. It is a test set, not an estimate of a real repository.
