# Data for project 35

Synthetic. Generated by `_generate.py` with a fixed seed (`SEED = 20261023`), so a rerun reproduces every file byte for byte. Nothing here comes from a real bank, intake process, catalog or vendor. Dataset names, units and use cases are invented.

**The reference tier is the rubric on the true inputs.** Points: customer-facing yes 2; autonomy advisory 0, assisted 1, automated 3; data class public 0, internal 1, confidential 2, restricted 3; vendor model none 0, self_hosted 1, vendor_api 2; regulatory scope none 0, privacy 1, aml 2, udaap 2, fair_lending 3; exposure band lt_1m 0, 1m_10m 1, 10m_50m 2, gt_50m 3. Tier = min(4, 1 + points // 4). 🟡 The points and cut-offs are my assumption, carried over from [project 11](../../11-tiergate-ai-usecase-intake/). Every accuracy figure measures recovery of that result from noisy inputs. It does not measure how real banks tier AI use cases.

| File | Rows | What it holds |
|---|---|---|
| `intake_submissions.csv` | 200 | The form columns a sponsor fills in, then hidden truth columns |
| `data_catalog.csv` | 25 | Dataset, the class the catalog records, the true class and a status |
| `vendor_registry.csv` | 78 | Use case to vendor model, accurate wherever it has an entry |
| `example_intake.csv`, `example_catalog.csv`, `example_registry.csv` | 6, 6, 2 | Hand-written forms behind `python3 tiergate.py --demo` |

## `intake_submissions.csv`

Visible to the tool: `use_case_id`, `sponsor_unit` (not read), `title`, `description`, `dataset_name`, `customer_facing` (yes, no, unsure or blank), `decision_autonomy`, `data_class`, `vendor_model`, `regulatory_scope`, `financial_exposure_band`, `self_declared_tier`. Hidden, read only to score: `true_customer_facing`, `true_data_class`, `true_vendor_model`, `reference_score`, `reference_tier`, `planted`. A test confirms the tool gives the same output with the hidden columns removed.

Autonomy, regulatory scope and exposure are copied from the truth with no error, so the tool cannot be wrong about them here and has no second source for them.

## How the forms go wrong (generator parameters I chose, with the realized count)

| What goes wrong on the form | Parameter | Realized |
|---|---|---|
| Data class set one level below the true class | internal 8%, confidential 25%, restricted 35% | 52 forms |
| Vendor dependency written as `none` | self_hosted 15%, vendor_api 30% | 30 forms |
| Customer-facing answer wrong, blank or `unsure` | true yes: 20% `no`, 8% `unsure`, 5% blank; true no: 3% `yes`, 4% `unsure`, 2% blank | 34 forms |
| Declared tier shaded from the sponsor's own rubric result on the form | down one tier 16% (above tier 1), up one tier 3% (below tier 4) | 20 down, 6 up |

The sponsor's own result is the rubric on the answers as written, where a blank or `unsure` customer-facing answer scores 0.

## Second sources

`data_catalog.csv` has 27 datasets in the generator and 25 rows in the file. Five entries are wrong on purpose: 3 understate the true class (`stale_understated`) and 2 overstate it (`stale_overstated`). Two datasets have no row (`not_listed`). The registry lists a vendor-dependent use case with probability 60% and lists only vendor-dependent use cases.

## Planted situations (the `planted` column)

The label is written from the generator's own inputs, not from what the rules print. A form can carry more than one. Counts on this seed:

| Tag | Kind | Forms |
|---|---|---|
| `class_understated_in_form_and_catalog` | hard case: the catalog entry is stale and understates the class too | 6 |
| `class_understated_dataset_not_listed` | hard case: the form understates the class and the catalog has no entry | 3 |
| `vendor_omitted_and_not_in_registry` | hard case: vendor dependency missing from the form and the registry | 16 |
| `customer_facing_denied_and_text_silent` | hard case: the form says internal, the tool is customer-facing, the text names nobody | 2 |
| `text_names_customers_but_internal` | hard negative: the text names customers and the tool is internal | 22 |
| `catalog_overstates_class` | hard negative: the catalog entry overstates the class | 16 |

A planted situation does not always change the tier: an understated class that stays inside the same tier band is not a miss. Step 4 prints, per tag, how many end up below or above the reference.

## What this data does not do

- It does not model real sponsor behavior, real catalogs or real registries. Every rate above is a parameter.
- The catalog and the registry are never wrong where they have an entry, apart from the five stale catalog entries. A real environment would be less tidy.
- The same author wrote the generator and the rules in `src/tiergate.py`, including the words the customer-facing rule looks for. The numbers are a ceiling, not a rate on real data.
- The descriptions come from 25 archetypes with one or two phrasings each. The text rule therefore measures how it behaves on this wording, not on free text from real sponsors.
