# Data for project 31

Synthetic. Generated by `_generate.py` with `SEED = 20261031`, so a rerun reproduces every file byte for byte (standard library only, one seeded `random.Random`). Nothing here comes from a real bank, vendor, person or intake issue. Dataset names, units and use cases are invented.

**The reference tier is true by construction.** It is the rubric below applied to the hidden true attributes of each issue. Every accuracy number measures how well a method recovers that tier from the issue body. It does not measure how real teams tier AI use cases. The error rates are parameters I chose, not observations.

## The rubric (an assumption, carried over from project 11)

Points on six answers, summed: customer-facing yes 2; decision autonomy advisory 0, assisted 1, automated 3; data class public 0, internal 1, confidential 2, restricted 3; vendor model none 0, self_hosted 1, vendor_api 2; regulatory scope none 0, privacy 1, aml 2, udaap 2, fair_lending 3; financial exposure band lt_1m 0, 1m_10m 1, 10m_50m 2, gt_50m 3. **Tier = min(4, 1 + points // 4).** The maximum is 16. The FINOS heuristic page defines no tiers or scores, so these points are mine, not FINOS's.

## Files

| `example_issue.md`, `example_labels.json` | The worked example behind `python3 intake_tier_action.py --demo` (issue 301, which is not in the 160) |

## How a body is made

The sponsor's answers are the truth plus injected errors, rendered the way an issue form renders them: `### label`, a blank line, the answer, `_No response_` for an empty one. Then the body is damaged in documented ways.

| Body kind | Count | What happened |
|---|---|---|
| `ok` | 142 | Intact. 13 of these have odd case or padding on the dropdown values and 16 use Windows line endings |
| `renamed_heading` | 5 | One required heading was renamed by hand, so that input is missing |
| `no_form` | 3 | Opened through the API with plain text and no headings |
| `truncated` | 6 | The body is cut inside the span that holds the autonomy to exposure answers |
| `pasted_heading` | 4 | The summary contains a pasted block that repeats the `Data class` heading with a different value. The form itself is complete |

24 issues were edited: the sponsor corrects the data class and the customer-facing answer and removes any pasted block, and leaves the vendor answer and the declared tier alone. 9 summaries carry a hostile line (a line starting with `::`, a mention, a tag or a link).

## Injected error on the form

| What goes wrong | Parameter |
|---|---|
| Data class one level below the true class | internal 8%, confidential 28%, restricted 32% |
| Vendor model left as `none` | vendor_api 30%, self_hosted 15% |
| Customer-facing answer wrong, unsure or blank | true yes: 20% no, 7% unsure, 5% blank. True no: 3% yes, 4% unsure, 3% blank |
| Declared tier shaded from the sponsor's own rubric result (unsure and blank score 0) | down one tier 20% (above tier 1), up one tier 3% (below tier 4) |
| Dataset name left blank | 4% |

A summary mentions a customer, client, borrower or similar word with probability 85% for a customer-facing use case, 60% for an internal use case whose subject is customer material, and 4% otherwise; 5 of the 18 use-case types have no customer wording at all. The cue check therefore measures how it behaves on this synthetic text, not on real text.

## What this data does not do

- It does not model real sponsor behavior, real catalogs, real registries or real review effort. Every rate is a parameter.
- It does not inject error into autonomy, regulatory scope or exposure, so the tool has no second source for them and cannot be wrong about them here.
- The registry is never wrong where it has an entry. A real one would be.
- The body format is my reconstruction of what an issue form writes. It has not been compared with a real GitHub issue.
