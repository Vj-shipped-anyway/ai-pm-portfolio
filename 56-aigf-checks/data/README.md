# Data for project 56

Synthetic. Generated by `_generate.py` with a fixed seed (56), so a rerun reproduces every file byte for byte. Nothing here comes from an employer, a customer, a real bank or a real framework entry. The 24 risks are paraphrases written for this exercise; the 20 checks, their commands and the text they print are invented.

| File | What it holds |
|---|---|
| `risks.csv` | 24 risks: `risk_id`, `title`, `summary`, `aspects` (what a check must exercise to cover the risk, separated by `;`) |
| `checks.csv` | 20 checks: `check_id`, `project`, `command`, `exercises` (the aspects the registry says the check exercises) |
| `check_outputs.json` | The text 17 of the 20 checks printed, by `check_id`. Three checks have no captured output on purpose |
| `crosswalk.csv` | 73 rows: `row_id`, `risk_id`, `check_id`, `covers` (full or partial), `claim_label`, `claim_value`, `note` |
| `row_truth.csv` | The planted kind of each row, whether it is defective, the finding an ideal tool would report, whether its proof holds and the coverage it really gives |
| `risk_truth.csv` | The status each risk should get, derived from the planted rows: CHECKED 16, PARTIAL 3, UNVERIFIED 2, GAP 3 |
| `check_truth.csv` | The aspects each check really exercises. Two checks, `C-18` and `C-19`, declare one aspect they do not exercise |
| `example_*.csv`, `example_outputs.json` | The worked example behind `python3 aigf_checks.py --demo`: 4 risks, 3 checks, 5 rows |

The truth comes from the way each row was built, not from a rule in `src/aigf_checks.py`: a row is built to carry one planted defect or none, and the risk-level truth is derived from those labels. The same author wrote the data and the rules, so the scores are a ceiling, not a rate on a real crosswalk.

Planted kinds (73 rows): ok 14, ok_reformatted 6, ok_negated_word 3, ok_partial 5, stale_value 10, label_missing 4, unknown_check 3, unknown_risk 3, overclaim 7, no_output 4, duplicate 3, wording_claim 4, wording_paraphrase 3, false_declaration 4. That is 28 harmless rows and 45 defective ones.

- Hard negatives, which a rule could flag by mistake: `ok_reformatted` (the check prints Title Case labels and thousands separators; the claim does not), `ok_negated_word` (the note says "non-compliant" while describing what the check lists), `ok_partial` (the row honestly says partial).
- Traps for a plain search: half of the 10 stale rows claim a number that is the tail of the true one, so it is a substring of the printed value; the 4 `label_missing` rows claim a value that the output does print, under a different label.
- Hard cases the rules miss: `wording_paraphrase` (an overclaim in words the rule does not list) and `false_declaration` (the registry declares an aspect the check does not exercise).

Gaps: `R-12`, `R-19` and `R-24` get no row on purpose; `R-24` needs an aspect (`availability`) that no check exercises.

To use your own data, keep the columns of `risks.csv`, `checks.csv`, `crosswalk.csv` and `check_outputs.json`. The truth files exist only because the data is synthetic.
