# Data for project 65

Synthetic. Generated by `_generate.py` with a fixed seed, so a rerun reproduces every file byte for byte. Nothing here comes from a real bank, vendor, outage or drill. Service names are generic functions (an authorization gateway, a ledger poster), not products. The date the data is judged against is 2026-10-24, a constant in the generator.

| File | What it holds |
|---|---|
| `services.csv` | 48 services: `service_id`, `name`, `domain`, `tier`, the primary and secondary region, `failover_mode`, `rto_target_min`, `config_version`, `depends_on` (declared hard dependencies, `;` separated), `accepted_risk`, and `failover_plan` (the owner's own claim, used only by step 1). 18 are tier 1, 24 tier 2, 6 tier 3 |
| `drills.csv` | 54 drill rows: date, `drill_type` (live or tabletop), `scenario`, the region failed over to, the config version it ran on, `minutes_to_recover`, `outcome` (pass, fail or partial) and `failure_reason`. 51 are live and 3 are tabletop |
| `service_truth.csv` | The planted truth per service: `story`, `truth_class` (ready, not_ready or accepted) and `hidden_depends_on`, the dependency the map leaves out. The label comes from the story planted for the service, not from the readiness rule |
| `example_services.csv`, `example_drills.csv` | The 8 services and 7 drills behind `python3 failover_scorecard.py --demo` |

Totals: 16 ready, 28 not ready, 4 accepted. Three kinds are hard on purpose: the three hard negatives (10 services) test for a false alarm, and `hidden_dependency` (3 services) tests for a miss the rule cannot avoid.

## Assumptions (🟡 modeled, mine)

No rule or standard that I read sets any of these. They are in the code as `default_policy()` and in the generator as `WINDOW`.

- Longest age of a passing drill: 180 days for tier 1, 365 for tier 2, 540 for tier 3.
- An owner may accept having no way back only for tier 3.
- Which scenario a mode needs: `active_active` and `warm_standby` need a live `region_failover` drill; `cold_restore` needs a live `backup_restore` drill.
- Recovery-time targets (30 or 60 minutes for tier 1, 120 or 240 for tier 2, 480 for tier 3), drill dates and minutes are invented.
- `depends_on` lists hard dependencies only: services that must be serving in the secondary region for this one to serve.

The windows in the generator and in the rule are the same assumption written twice. The planted `stale_drill` and `proven_old_unchanged` services sit on either side of it, so changing the window changes the numbers (step 4 prints the tier-1 count at 90, 180 and 365 days).
