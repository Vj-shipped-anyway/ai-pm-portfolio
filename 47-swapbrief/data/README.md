# Data for project 47

Synthetic. Generated by `_generate.py` with fixed seeds, so a rerun reproduces every file byte for byte. Nothing here comes from a real model, vendor, bank or employer. No model was called. The generator is a stub that stands in for real evaluation runs, with the true effects written down so a decision rule can be scored against them. The rules in `src/swapbrief.py` never read the truth.

```bash
cd data && python3 _generate.py     # about 6 seconds
```

| File | What it holds |
|---|---|
| `results.csv` | The committed set and the first input file of the contract: 600 items scored under two systems, `incumbent` and `successor` (1,200 rows). Columns: `item_id`, `slice`, `system`, `correct`, `input_tokens`, `output_tokens`, `latency_ms`. |
| `prices.csv` | The second input file: one row per system, `input_usd_per_1k` and `output_usd_per_1k`. Parameters, not vendor prices. The successor's list price is 0.85 of the incumbent's. |
| `slices.csv` | The 6 slices of a back-office case-handling assistant, which are critical (`card_disputes`, `wire_exceptions`, `kyc_refresh`), their sizes and a one-line description. `account_closure` has 40 items on purpose, as if those cases were slow to grade. |
| `committed_truth.csv` | The planted true accuracy per slice for the committed set. Scoring only: no rule reads it. Five slices improve by 3 to 7 pp; `account_closure` falls 8.0 pp. |
| `committed_world.json` | The planted answer-length multiplier (2.4), slow-path rate (0.10) and price ratio (0.85) of the committed set, and the true cost-per-correct-answer ratio (1.35), true p50 ratio (1.001) and true p95 ratio (2.018). |
| `scenario_truth.csv` | 80 simulated migrations, each a different world: its size, answer length, slow-path rate, price ratio, the number of truly regressing slices, the true cost and p95 ratios, and four labels (`bad_slice`, `bad_cost`, `bad_p95`, `bad`). |

## How the process is built

For each item a shared latent difficulty makes the two systems' outcomes correlated, as they are when one evaluation set is run against two model versions (shared share 0.60). The successor counts about 3% more input tokens for the same text and writes answers a multiple longer than the incumbent's. Latency is a base time (first token plus a per-token time) times lognormal noise, and a share of calls hit a slow path that multiplies it. The incumbent has a 3% slow path of 1.5 to 2.2 times; the successor has its scenario's rate with a 3 to 6 times multiplier. Every parameter is synthetic.

Each scenario draws its own world from `SCENARIO_SEED + i`: slice sizes scaled by 0.75, 1.0 or 1.5; each slice regressing with probability 0.06 (a fall of 6 to 14 pp), flat with probability 0.25, otherwise improving by 2 to 10 pp; answer length 1.0, 1.4, 2.0 or 2.6 times; slow-path rate 0.02, 0.05, 0.08 or 0.12; price ratio 0.75, 0.85 or 1.0. The evaluation sample for scenario `i` is a separate draw from `SAMPLE_SEED + i`, so the planted truth and the sample the rules see are different random outcomes of the same world.

## How truth is labeled

A migration carries a real problem when, in the true world, any slice falls 5 pp or more, or cost per correct answer rises 10% or more, or p95 rises 25% or more. Those three levels are mine (assumptions, not taken from any rule). Accuracy and cost are exact from the parameters. The p50 and p95 ratios are measured on 10,000 fresh draws from the world, not on the evaluation sample, so they carry a little sampling error themselves.

Of the 80 scenarios, 45 carry a real problem: 25 have a regressing slice, 26 a cost problem and 11 a p95 problem (they overlap).

## Planted hard cases

Two kinds of scenario are planted on a schedule, and `scenario_truth.csv` names them in its `kind` column.

- `hard_negative` (scenarios 10, 20, up to 80): a good migration. Every slice improves, the slow-path rate is 0.02, and the answer-length multiplier is solved so that the true cost per correct answer lands between 1.06x and 1.09x, just under the 1.10x line. A tool with a watch level at 1.05x can raise a false alarm here.
- `hard_miss` (scenarios 5, 15, up to 75): a real fall of 7 to 10 pp in `account_closure`, the smallest slice (30 items at the 0.75 scale), in an otherwise clean migration. A tool that cannot resolve 30 items can miss it.

The other 64 scenarios are drawn from the scenario mix above with no planting.
