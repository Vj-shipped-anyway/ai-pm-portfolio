# Data for project 37

Synthetic. Generated by `_generate.py` with `SEED = 37`, so a rerun reproduces every file byte for byte. Nothing here comes from a real bank, customer, employee, system or vendor. Document text is built from templates by the generator, not by a model.

**The truth is known because the data is synthetic.** The generator decides every access list and the label of every pull request. It computes who may open what by walking the group tree downward from each ACL group; the resolver in `src/entitlement_canary.py` walks upward from the user, and the toy system in `src/common.py` has a third check (also downward, written separately). Their agreement is by construction: it shows none of them is buggy, and says nothing about a real directory that is wrong.

| File | What it holds |
|---|---|
| `access_base.json` | The access export the tool reads: 18 groups (nested up to 4 levels, one group with two parents), 20 users (6 contractors), 120 documents with `acl` and `acl_at_index` |
| `doc_text.csv` | The text of each document, used by the toy system's index and by the string-match step |
| `queries.csv` | 96 relevance-eval queries: `query_id`, `user_id`, `text`, `relevant_doc_ids` (every document on the topic, whoever may read it) |
| `entitlement_truth.csv` | For each user, the documents the user may open today (20 users by 120 documents, 1028 pairs open) |
| `pr_cases.csv` | 50 pull requests: `pr_id`, `config_json` (the settings the change moves), `access_patch_json` (ACL changes made in the same pull request) |
| `pr_truth.csv` | The planted change per pull request: `change_kind` and `truth_leaks`. The label comes from the change that was planted, not from the canary rules |
| `example_access.json`, `example_pack.csv`, `example_results.csv` | The worked example behind `python3 entitlement_canary.py --demo` (5 documents, one nested-deny leak) |

## Shape

- Documents: 120, from 12 topics with 5 aspects each and 2 documents per aspect. Sources: dms 47, wiki 35, tickets 25, policy 10, minutes 3. Eight documents quote another document's title in their text.
- Access: 57 documents carry a deny entry (`-grp-contractors`, `-grp-contractors-tech`, `-grp-contractors-ops`, `-grp-retail-cards` or `-grp-hr`). Contractors reach `grp-contractors` only through nesting, which is what a flat group check misses.
- Index copy: 19 documents have an `acl_at_index` that differs from `acl` (12 gained a deny entry since, 7 lost a group). 26 (user, document) pairs were open under the index copy and are closed today.
- Flat-group exposure: 9 pairs are closed today but open if only direct group membership is read.

## Planted changes (50)

Leaking (28): deny entries ignored 5 (`deny_ignored`), flat group check 5 (`flat_groups`), ACL copy from index time 4 (`index_acl_copy`), answer cache shared between users 5 (`shared_cache`), a source ingested without its ACLs 5 (`new_source_no_acl`), delegation that lends a boss's access over one group 4 (`delegation_inherit`).

Clean (22): a source removed from the index 3 (`source_unindexed`), ranking and filter-order settings 6 (`rerank_change`), extra documents withheld from contractors 4 (`stricter_filter`), answer cache keyed by user 4 (`per_user_cache`), an ACL change that grants access 5 (`acl_grant`).

Hard on purpose: `delegation_inherit` leaks one (user, document) pair per pull request, so a pack of sixty canaries usually misses it. The five clean kinds change what comes back without leaking, and each could raise a false alarm in a naive check: `acl_grant` turns a canary pair into a pair the user may open; `source_unindexed` makes a source's canaries untestable.

## Seed and design choices, stated

I chose the seed once and did not try another. I changed the design before the generator's own checks passed: the first estate had too few stale-ACL and nested-deny pairs, so I added two contractors, raised the share of documents with a deny entry, and moved the contractors' department groups to the groups that own the most documents. I changed the prime-user rule after the first run: it picked the lowest user id, which is a contractor, and a clean pull request that withheld ticket documents from contractors came back as REVIEW. The pack now primes with the user who may open the target and can open the most documents. Both changes came after I looked at results from earlier versions of the rules, so the final numbers are tuned to this data to that degree.

Counts over this data describe this data. The leak rate, the number of stale pairs and the share of documents with a deny entry are properties of the generator, not estimates of any real environment.
